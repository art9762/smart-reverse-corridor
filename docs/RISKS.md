# Риски на сцене и план Б

Этот документ — про живое выступление, не про эксплуатацию. Цель: на каждый риск иметь заранее заготовленный план Б, чтобы спикер не импровизировал под прожекторами.

## Подробно

### 1. Нет интернета
- Все сервисы работают локально.
- `scripts/seed_videos.sh` не используется на сцене — это инструкция для подготовки.
- Дашборд читает MQTT по WebSocket с того же ноутбука.
- Перед выходом: `airplane mode on`, проверить, что всё ещё работает.

### 2. HDMI/проектор
- Иметь USB-C → HDMI и USB-C → DisplayPort.
- Иметь второй ноутбук с тем же снапшотом (git pull до начала, не во время).
- Если совсем плохо — спикер показывает PDF слайды без живого демо, видео из плана 3.

### 3. Стек не стартует
- На запасном диске (или у каждого члена команды на ноуте) лежит `docs/demo_fallback.mp4` — полная запись прогона: baseline, adaptive, фура, скорая, потеря камеры.
- Длительность ровно 4:30, чтобы вписаться в тайминг.
- В `docs/demo_fallback_metrics.png` — те же графики, что и в живом демо.
- Спикер говорит фразу из конца `PITCH_OUTLINE.md`: «Чтобы не зависеть от железа на сцене…».

### 4. MQTT-брокер
- Если docker не отзывается за 10 секунд: `mosquitto -c infra/mosquitto/mosquitto.conf -v` запускает брокер вручную.
- Контроллер автоматически переподключается (см. backoff в `services/controller/`).

### 5. ML тяжёлый
- В `make demo` по умолчанию ML **выключен** — события шлёт симулятор по тому же MQTT-контракту.
- Это специально: на сцене мы показываем алгоритм управления, а не нагрузку GPU.
- ML включается ключом `make demo-with-ml` для отдельной демонстрации в кулуарах.

### 6. Видео-датасет
- На сцене не нужен.
- В кулуарах для жюри-эксперта — показать YOLO+ByteTrack на одном коротком клипе из `data/videos/cam_A_in.mp4`, если он подготовлен.

### 7. Сбой FSM в проде
- В UI есть кнопка «Безопасный режим» → `POST /override {action: "force_phase", phase: "RED_BOTH"}`.
- Контроллер при потере связи с обеими камерами на стороне сам уходит в `RED_BOTH` (см. `FSM.md`).
- Это рассказать, если жюри спросит «а если у вас CV ошибся?» — ответ: «решение принимается консервативно, лишний red лучше лишнего green».

### 8. Тайминг
- Спикер видит секундомер. Если на 3:30 ещё не показали adaptive — пропустить «спецтранспорт» и сразу к цифрам.
- Запасной короткий вариант питча — 3 минуты — лежит в конце `PITCH_OUTLINE.md` как комментарии (TODO: добавить, если попросят).

### 9. Лицензия данных
- Подготовить ответ: «Все видео — публичные исследовательские датасеты (UA-DETRAC, MIO-TCD, AI City Challenge) или CC0 (Pexels). Лицензии перечислены в `scripts/seed_videos.sh`.»

### 10. Команда
- Дублёр спикера читает `PITCH_OUTLINE.md` без подготовки — текст самодостаточен.
- Демо-оператор работает с парой кнопок: «mode toggle», «scenario start», «emergency».

## Боевая последовательность

1. T-30 мин: `git pull`, `make up`, проверка дашборда.
2. T-15 мин: прогнать `tests/integration/test_basic_flow.py` локально, если время есть.
3. T-10 мин: открыть `docs/demo_fallback.mp4` в плеере на втором экране (не закрывать).
4. T-3 мин: уведомления off, заряд проверен, презентация в полноэкранном режиме.
5. На сцене: спикер на микрофоне, оператор у ноутбука. Никто кроме оператора ноута не трогает.
6. После: краткое ретро — что сработало, что нет, обновить этот файл.
