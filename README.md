# Умный реверсивный коридор

Программный прототип для кейса ИТ-чемпионата «Цифровая Эра Транспорта» 2026:
симуляция поочерёдного движения по участку ремонта, контроллер фаз, обработка camera events
и веб-дашборд для демонстрации.

Подтверждены проверки программных компонентов и синтетических сценариев. Проект не прошёл
валидацию для управления реальными светофорами и не должен представляться как готовая
система предотвращения ДТП. Текущие ограничения и критерии следующего этапа — в [плане работ](PLAN.md).

## Как устроен прототип

1. Симулятор создаёт транспорт и camera events. ML/CV-сервис может формировать тот же контракт
   из видео: YOLOv8 детектирует объекты, собственный IoU-трекер связывает их между кадрами.
2. Контроллер получает MQTT-события, ведёт счётчики и запускает FSM с фиксированными либо
   адаптивными длительностями зелёного.
3. В обычных переходах FSM проверяет пустоту зоны и интервал после жёлтого. Отдельный fallback
   при потере камер обходит часть этой проверки; его согласование с инвариантом — задача P0 в плане.
4. Контроллер публикует состояние, метрики и alerts; симулятор отдельно передаёт позиции транспорта.
   React-дашборд отображает их и позволяет отправлять demo-команды.

```text
Видео → ML/CV ─┐
              ├─ MQTT → Контроллер FSM → REST / WS → Web
Симулятор ────┘              └─ SQLite / InfluxDB → Grafana
    └─ MQTT world snapshots → Web
```

## Локальный запуск

Нужны Docker с Compose, Make и свободные порты из `.env.example`. Это dev-конфигурация;
указанные по умолчанию пароли и открытые интерфейсы предназначены для изолированного стенда.

```bash
git clone https://github.com/art9762/smart-reverse-corridor.git
cd smart-reverse-corridor
cp .env.example .env
make up      # mosquitto, influxdb, controller, web, grafana
make demo    # добавляет симулятор asymmetric в adaptive-режиме
```

Адреса по умолчанию: [дашборд](http://localhost:5173), [API](http://localhost:8000/health),
[Grafana](http://localhost:3001). `make demo` выводит логи; браузер открывается вручную.
ML-сервис включается отдельно через Compose profile `ml`.

Альтернативный launcher использует сценарий `showcase` по умолчанию:

```bash
bash scripts/demo.sh
bash scripts/demo-stop.sh
```

Параметры геометрии, интенсивности и времени фаз описаны в `.env.example`,
[документации симулятора](services/simulator/README.md) и [контроллера](services/controller/README.md).

## Проверки и статус

Локально прошли 54 теста контроллера, 22 симулятора, 16 ML/CV, headless-симуляция без брокера
и офлайн-проверка повторной доставки выхода. [CI программного изменения](https://github.com/art9762/smart-reverse-corridor/actions/runs/39945864808)
также подтвердил Python 3.11/3.12, web-тесты/сборку, Compose config и сборку четырёх образов.
Это не проверка работающего целиком стека или качества распознавания реального видео.

Команды для отдельных компонентов:

```bash
(cd services/controller && python -m pytest -q)
(cd services/simulator && python -m pytest -q)
(cd services/ml && python -m pytest -q)
(cd web && npm ci && npm test && npm run lint && npm run build)
```

Python-зависимости устанавливаются в отдельное окружение для каждого сервиса по его README.
Для [ML unit-тестов](services/ml/README.md) достаточно `requirements-test.txt`: модель и видео
не нужны. В текущем Makefile неуспех Python-теста может маскироваться; до исправления используйте
прямые команды выше. Ruff-долг также пока не блокирует CI.

## Демо-сценарии и метрики

Симулятор включает симметричный и асимметричный поток, грузовой трафик, приоритет спецтранспорта,
потерю камеры и застревание транспорта. Это сценарии для исследования поведения программы.

Метрики контроллера пока требуют уточнения: `queue` отражает occupancy, а `avg_delay`
вычисляется из времени между въездом и выездом. [Sample results](scripts/generate_sample_results.py)
создаются отдельной упрощённой моделью. Их нельзя выдавать за измерения выигрыша работающего
контроллера; критерии корректного сравнения перечислены в [PLAN.md](PLAN.md).
